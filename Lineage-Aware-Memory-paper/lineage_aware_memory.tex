% ── Abstract ─────────────────────────────────────────────────────────────────
\begin{abstract}
\noindent
Shared memory across AI agents offers large efficiency gains in enterprise analytics,
but introduces two underexplored failure modes: unauthorized data leakage when an
agent retrieves an insight derived from columns it cannot access, and silent
metric-definition conflicts when teams compute the same KPI through divergent
derivation paths.
Existing systems---MemGPT~\citep{packer2023memgpt}, Zep~\citep{rasmussen2025zep},
A-MEM~\citep{xu2025amem}, SSGM~\citep{lam2026ssgm},
Governed Memory~\citep{taheri2026governed},
and Oracle AI Agent Memory~\citep{oracle2026memory}---govern content and access tags
but none track \emph{how} a stored result was derived.
We propose the \emph{Analytical Memory Unit} (AMU), a schema extension that attaches
a derivation graph to every stored result, paired with a \emph{lineage-gated retrieval}
policy: a memory hit is served only when the requesting department is permitted to see
every column in the derivation path.
We prove formally that this policy provides a complete column-level safety guarantee
under honest lineage recording (\S\ref{sec:formal}),
analyse its $O(n)$ worst-case retrieval complexity and
$4$--$8\times$ storage overhead relative to a bare value entry,
and construct a threat model delineating scope (\S\ref{sec:threat}).
Controlled simulation on a 5-table synthetic schema and an 8-table
TPC-H-inspired schema~\citep{tpch2021}, each run under 30 random seeds,
shows that content-gated memory leaks on $18.8\%$ and $25.5\%$ of
cross-department retrievals respectively; lineage-aware gating eliminates
leakage in both configurations while retaining $82.6\%$ and $81.5\%$ memory reuse.
A secondary experiment on 10 hand-labelled lineage pairs shows that exact hash
matching has precision $0.50$ against threshold-variant pairs;
a column-graph detector achieves perfect precision and recall by correctly
treating same-schema threshold changes as non-conflicting variants.
\end{abstract}

\noindent\textbf{Keywords:}
AI agent memory; data lineage; enterprise data governance; column-level access
control; multi-agent systems; business intelligence; privacy in ML systems.\\[2pt]
\noindent\textbf{arXiv categories (suggested):} cs.AI; cs.DB; cs.CR

\section{Introduction}
\label{sec:intro}
% =============================================================================

Over the past two years, large language model (LLM) agents have moved from research
prototypes to production components inside enterprise data stacks.
Teams at organisations of all sizes now run agents that generate analytical summaries,
write SQL, and produce business metrics---often querying the same underlying tables
and reporting against the same KPIs.
Sharing memory across these agents is a natural optimisation: if Finance already
computed this quarter's churn rate, why should Marketing recompute it from scratch?

The appeal is genuine.
Systems like MemGPT~\citep{packer2023memgpt}, Zep~\citep{rasmussen2025zep},
A-MEM~\citep{xu2025amem}, and Oracle AI Agent Memory~\citep{oracle2026memory} have
demonstrated that shared, persistent memory can dramatically reduce redundant
computation and improve response consistency.
Governed Memory~\citep{taheri2026governed} and the SSGM
framework~\citep{lam2026ssgm} have begun to address the governance layer, introducing
access controls and stability checks for evolving memory stores.
Du's recent survey~\citep{du2026survey} provides a structured account of the field.

But every current approach controls access at the level of \emph{content} and
\emph{tags}, not \emph{derivation}.
A memory entry is labelled with its owner, a sensitivity class, or a role-based
tag, and retrieval is gated on whether the requester holds the right label.
None of these systems record which tables were joined, which columns were touched,
or what filter logic was applied to produce the stored result.

This gap has concrete consequences.
Consider a Finance agent that computes a high-value customer segment by joining
\texttt{customer\_pii} (containing \texttt{income}) against \texttt{transactions}.
The result---12{,}400 high-value customers---contains no PII and carries no
sensitivity tag.
Under content-based governance it is served freely to a Marketing agent.
But Marketing cannot see \texttt{income}.
The derivation path violated column-level access policy, silently.

A second failure mode compounds the first.
Different departments often compute the same KPI through genuinely different logic.
Finance might define churn as ``no transaction in 90 days,'' while Marketing uses
a 60-day window adjusted for income segment.
Both call the metric \texttt{churn\_rate}.
Without derivation tracking, shared memory silently propagates one team's
definition to the other.

\paragraph{Contributions.}
\begin{enumerate}[leftmargin=1.5em,itemsep=1pt]
  \item We define the \emph{Analytical Memory Unit} (AMU) schema and the
        \emph{lineage-gated retrieval} policy (\S\ref{sec:design}).
  \item We provide a formal safety proof and complexity analysis (\S\ref{sec:formal}).
  \item We construct a threat model (\S\ref{sec:threat}).
  \item We present controlled experiments on two schema configurations and a
        fuzzy conflict-detection study (\S\ref{sec:experiments}).
\end{enumerate}

\section{Related Work}
\label{sec:related}
% =============================================================================

\subsection{Memory Systems for LLM Agents}

Du~\citep{du2026survey} formalises agent memory as a write-manage-read loop with
a three-dimensional taxonomy spanning temporal scope, representational substrate,
and control policy.
MemGPT~\citep{packer2023memgpt} instantiated the hierarchy by treating the LLM as
an OS that pages between a bounded context window and an external store via function
calls, demonstrating coherent long-horizon conversations and large-document analysis.
Governance in MemGPT is implicit: the LLM decides what to write and retrieve, with
no lineage tracking at any layer.

Zep~\citep{rasmussen2025zep} introduced a temporal knowledge graph with dual-axis
timestamping (event time vs.\ ingestion time), enabling point-in-time queries.
Its graph captures \emph{when} information arrived, not \emph{how} it was derived.
A-MEM~\citep{xu2025amem}---a NeurIPS 2025 paper---builds Zettelkasten-style linked
notes with dynamic indexing, achieving strong benchmark performance across six
foundation models.
Linking structure encodes semantic relatedness rather than data derivation.

\paragraph{Explicit contrast with our work.}
All three systems represent the state of the art in conversational or task-level
memory.
They are well-suited to remembering facts, past conversations, and user preferences.
None model the data provenance of computed analytical results, and none can detect
that a stored insight was derived from a column the requester cannot see.
The AMU schema is not a replacement but an extension for the analytical-result-caching
use case in enterprise data environments.

\subsection{Governed and Enterprise Memory Architectures}

Taheri's Governed Memory~\citep{taheri2026governed} addresses a real enterprise
gap---dozens of agents operating with no shared memory and no common
governance---through a dual memory model, tiered governance routing, and a
closed-loop schema lifecycle.
In a 250-event controlled experiment, it achieves 99.6\% fact recall and zero
cross-entity leakage across 500 adversarial queries under its content-level
governance model.
Its governance operates on \emph{what is stored and who may access it}; our work
operates on \emph{how the stored value was derived}.
The two layers are orthogonal and composable.

Lam et al.'s SSGM~\citep{lam2026ssgm} decouples memory evolution from execution by
enforcing consistency verification, temporal decay modelling, and dynamic access
control before any memory consolidation.
SSGM's dynamic access control enforces agent-topology constraints (who may communicate
with whom); our lineage gate enforces column-level derivation constraints (what data
was touched to produce a result).
The two mechanisms complement each other.

Oracle AI Agent Memory~\citep{oracle2026memory} provides a commercially deployed
governed memory core with fine-grained lifecycle management and role-based access
controls.
Role assignment controls access to memory entries as a whole, not to the individual
columns that contributed to a stored result.

\subsection{Data Provenance and Lineage}

The W3C PROV standard~\citep{moreau2011prov} encodes entity-activity-agent
relationships for data provenance; Herschel et al.~\citep{herschel2017survey} survey
systems that use provenance to track data flow through complex pipelines---a problem
closely related to derivation-gated retrieval.
Column-level lineage extraction systems such as
LINEAGEX~\citep{zhang2025lineagex}---which parses SQL query trees to infer column-level
derivation with high coverage and accuracy, demonstrated at ICDE 2025---represent
the state of the art in automatic lineage extraction.
Our AMU schema applies the same concept to agent memory entries; LINEAGEX is the
natural tool for automatically populating AMU lineage fields in production.

The EU AI Act~\citep{euaiact2024}, which entered into force in August 2024, legally
mandates explainability and risk management for high-risk AI systems; data lineage
is widely recognised as a prerequisite for both properties.

\paragraph{Key gap.}
The provenance literature focuses on \emph{raw database records and pipelines}.
No prior work applies column-level provenance to \emph{agent memory retrieval
governance}, nor uses derivation graphs to gate cross-department memory sharing.
This is the gap we fill.

\subsection{Privacy Leakage in Multi-Agent Systems}

El Yagoubi et al.'s AgentLeak~\citep{elyagoubi2026agentleak}---the first full-stack
benchmark for privacy leakage in multi-agent LLM systems---shows that 68.8\% of
leakage occurs through inter-agent channels (messages, shared memory, tool arguments)
invisible to output-only auditors, across 4,979 validated execution traces.
Naik et al.'s OMNI-LEAK~\citep{naik2026omnileak} demonstrates that a single indirect
prompt injection can compromise several agents and leak sensitive data even with
data-access controls in place.

These works identify leakage through \emph{inter-agent communication channels}.
Our work identifies a complementary vector: leakage through a \emph{shared analytical
memory store} that persists even when every individual communication link is
correctly access-controlled.
The two failure modes are independent and both need to be addressed in production.

\subsection{Metric Definition Inconsistency}

Semantic drift---divergent definitions of the same KPI across teams---is a documented
source of dashboard inconsistency in enterprise BI~\citep{colrows2024metrics}.
Semantic layer tools (dbt Metrics, Databricks Unity Catalog, Looker LookML) address
this for human analysts by centralising metric definitions.
AI agents operating autonomously have no equivalent check.
Our \texttt{definition\_hash} conflict detector provides a foundation for automated
metric governance in agentic systems; the fuzzy experiment in \S\ref{sec:fuzzy}
characterises where hash-based detection is and is not the right granularity.

\section{System Design}
\label{sec:design}
% =============================================================================

\subsection{The Analytical Memory Unit}

\begin{definition}[Analytical Memory Unit]
An \emph{Analytical Memory Unit} (AMU) is a tuple
$\langle \mathit{metric}, v, d, \tau, L \rangle$ where:
$\mathit{metric}$ is a metric-name string;
$v \in \mathbb{R}$ is the computed result value;
$d$ is the producing department;
$\tau$ is an integer epoch (supports TTL eviction); and
$L = (s_1, \ldots, s_k)$ is a \emph{lineage graph}, each step
$s_i = (\mathit{table}_i,\, C_i,\, \varphi)$
where $C_i$ is the set of columns of $\mathit{table}_i$ accessed and
$\varphi$ is a filter-logic string.
\end{definition}

Two quantities are derived at creation time and cached:
\begin{align}
  \mathrm{S}(a) &= \bigcup_{i=1}^{k} C_i \;\cap\; \mathcal{S}
  \label{eq:sensitivity} \\[2pt]
  \mathrm{H}(a) &= \mathrm{SHA256}\!\left(
    \mathrm{sort}(\mathit{tables}) \,\|\,
    \mathrm{sort}\!\left(\bigcup_i C_i\right) \,\|\, \varphi
  \right)_{\![0{:}12]}
  \label{eq:defhash}
\end{align}
where $\mathcal{S}$ is the organisation's sensitive-column registry and
$\mathrm{H}(a)$ is the \emph{definition hash} that fingerprints
\emph{how} the metric was computed.
Full schema fields are listed in Table~\ref{tab:amu}.

\begin{table}[h]
\centering
\caption{Analytical Memory Unit (AMU) schema fields.}
\label{tab:amu}
\begin{tabular}{@{}lll@{}}
\toprule
\textbf{Field} & \textbf{Type} & \textbf{Description} \\
\midrule
\texttt{metric\_name}      & \texttt{str}      & Business KPI name (\emph{e.g.}, \texttt{churn\_rate}) \\
\texttt{value}             & \texttt{float}    & Computed result \\
\texttt{owner\_dept}       & \texttt{str}      & Producing department \\
\texttt{epoch}             & \texttt{int}      & Time index; enables TTL-based eviction \\
\texttt{lineage}           & \texttt{Lineage}  & Derivation graph: sequence of $(t, C, \varphi)$ steps \\
\texttt{sensitivity\_tags} & \texttt{Set[str]} & $\mathrm{S}(a)$: sensitive columns touched (Eq.~\ref{eq:sensitivity}) \\
\texttt{definition\_hash}  & \texttt{str}      & $\mathrm{H}(a)$: 12-char SHA-256 derivation fingerprint (Eq.~\ref{eq:defhash}) \\
\bottomrule
\end{tabular}
\end{table}

\subsection{Lineage-Gated Retrieval and Conflict Detection}
\label{sec:algorithms}

Algorithms~\ref{alg:retrieve} and~\ref{alg:write} give pseudocode for the two core
operations. $\mathrm{P}(d)$ denotes the permitted column set for department $d$.

% ── Algorithm 1 ──────────────────────────────────────────────────────────────
\begin{algorithmbox}[label={alg:retrieve}]{Lineage-Gated Retrieve}{%
  \textnormal{Input: \textit{store}, \textit{metric}, \textit{dept}, \textit{fresh}}%
  \quad Output: \textit{result}; \textit{leaked}=\textbf{False} guaranteed}
% store  : dict mapping metric-name -> list[AMU] (sorted oldest-first)
% metric : string KPI name requested
% dept   : requesting department identifier
% fresh  : a freshly computed AMU scoped entirely within P(dept)
%          (caller's responsibility; used only when no safe cached entry exists)

candidates <- store[metric]         % retrieve all stored AMUs for this metric
permitted  <- P(dept)               % column set the department may see
blocked    <- False

for each a in REVERSE(candidates):  % iterate most-recent-first
  if S(a) not_subset permitted:     % derivation touches a forbidden column
    blocked <- True
    continue                        % skip this candidate; try the next
  end if
  % Safe candidate found: all sensitive derivation columns are permitted
  return (reused=True, value=a.value, leaked=False, blocked=False)
end for

% No safe candidate in memory -- fall back to in-scope fresh computation
store[metric].append(fresh)
return (reused=False, value=fresh.value, leaked=False, blocked=blocked)
\end{algorithmbox}

% ── Algorithm 2 ──────────────────────────────────────────────────────────────
\begin{algorithmbox}[label={alg:write}]{Lineage-Aware Write with Conflict Detection}{%
  \textnormal{Input: \textit{store}, AMU \textit{a}} \quad
  Output: \textit{conflict} \textbf{bool}}
% store    : shared memory dict (mutated in place)
% a        : new AMU to persist
% conflict : True iff a cross-department definition conflict is detected

existing <- store[a.metric]   % all AMUs stored for this metric name
conflict <- False

for each e in existing:
  if e.dept != a.dept:        % cross-department pair
    if H(e) != H(a):          % definition hashes differ -> conflict
      conflict <- True
      break                   % one conflict is sufficient to raise the alert
    end if
  end if
end for

store[a.metric].append(a)     % always persist; conflict is surfaced, not blocked
return conflict
\end{algorithmbox}

The architecture is illustrated in Figure~\ref{fig:arch}.

\centering
\includegraphics[width=\linewidth]{fig2_architecture.png}
\caption{AMU architecture.
The lineage gate checks $\mathrm{S}(a) \subseteq \mathrm{P}(d)$ before serving

\section{Formal Analysis}
\label{sec:formal}
% =============================================================================

\subsection{Safety Guarantee}

\begin{assumption}[Complete Lineage]
\label{ass:complete}
For every AMU $a$ in the store, $a.\mathit{lineage}$ records every table, every
column, and the filter logic of the computation that produced $a.\mathit{value}$.
\end{assumption}

\begin{theorem}[Column-Level Safety]
\label{thm:safety}
Under Assumption~\ref{ass:complete}, Algorithm~\ref{alg:retrieve} returns no result
to department $d$ that was derived from a column $c \notin \mathrm{P}(d)$.
\end{theorem}

\begin{proof}
The algorithm has two exit paths; we show safety on each.

\smallskip\noindent\textbf{Memory-served path (line 13 of Algorithm~\ref{alg:retrieve}).}
The guard at line 9 must be false for the algorithm to reach line 13, meaning
$\mathrm{S}(a) \subseteq \mathrm{P}(d)$.
By Equation~\ref{eq:sensitivity},
$\mathrm{S}(a) = \bigl(\bigcup_i C_i\bigr) \cap \mathcal{S}$,
so the guard passing implies that every column in the derivation of $a$ that
belongs to the sensitive registry $\mathcal{S}$ is also in $\mathrm{P}(d)$.
Non-sensitive columns ($c \notin \mathcal{S}$) carry no access restriction by
the definition of $\mathcal{S}$.
Therefore, for any column $c$ that contributed to $a.\mathit{value}$:
either $c \in \mathcal{S}$ and $c \in \mathrm{P}(d)$ (allowed by the guard),
or $c \notin \mathcal{S}$ (unrestricted).
In particular, no column $c \notin \mathrm{P}(d)$ contributed.

\smallskip\noindent\textbf{Fallback path (line 20 of Algorithm~\ref{alg:retrieve}).}
The caller computes \textit{fresh} within $\mathrm{P}(d)$ by the stated input
precondition.
Under Assumption~\ref{ass:complete}, \textit{fresh}'s lineage touches no column
outside $\mathrm{P}(d)$.

\smallskip\noindent
Every result returned exits via one of these two paths, establishing the claim
for all invocations of Algorithm~\ref{alg:retrieve}.
\end{proof}

\begin{corollary}
The guarantee holds even when the store contains AMUs whose derivation paths
touch columns outside $\mathrm{P}(d)$: those candidates are skipped at line~9
and never returned.
\end{corollary}

\begin{remark}[Assumption dependency]
Assumption~\ref{ass:complete} is critical.
If lineage is reported by the computing agent rather than extracted automatically
from query execution plans, a buggy or adversarial agent can omit a column,
breaking the guarantee.
Automatic extraction via systems such as LINEAGEX~\citep{zhang2025lineagex} is
the appropriate production countermeasure; this dependency is also catalogued as
threat T5 in \S\ref{sec:threat}.
\end{remark}

\subsection{Asymptotic Complexity}
\label{sec:complexity}

Let $n$ = AMUs stored for a given metric name, $k$ = lineage steps per AMU,
$c$ = average columns per step.

\begin{table}[h]
\centering
\caption{Asymptotic complexity of AMU operations.}
\label{tab:complexity}
\begin{tabular}{@{}lll@{}}
\toprule
\textbf{Operation} & \textbf{Time} & \textbf{Notes} \\
\midrule
Sensitivity-tag derivation & $O(kc)$    & Computed once at AMU creation; cached \\
Definition-hash computation & $O(kc)$   & Single SHA-256 pass over sorted fields \\
Write --- conflict detection & $O(n)$   & Linear scan of existing AMUs for metric \\
Retrieve --- worst case      & $O(n)$   & All $n$ candidates blocked \\
Retrieve --- expected case   & $O(1)$   & Most-recent candidate safe; one check \\
\bottomrule
\end{tabular}
\end{table}

In practice $n \leq 5$ for any metric (at most one AMU per department variant),
so all operations are effectively $O(1)$.
The gate check itself---a set-difference over $|\mathrm{S}(a)| \leq |\mathcal{S}|$
elements---is dominated by the analytics query it governs.

\subsection{Storage Overhead}

A naive memory entry storing $(\mathit{metric}, v, d, \tau)$ requires roughly
50--80 bytes.
An AMU adds: $k$ tuples of table name and column names, the filter-logic string
$\varphi$, and the 12-character hash.
For a typical analytical query joining 2--4 tables and referencing 5--15 columns,
the lineage payload is 200--600 bytes---a $4$--$8\times$ overhead.
This is smaller than the SQL query most systems already persist alongside the
result, and is negligible relative to production vector-store capacities.

\section{Threat Model}
\label{sec:threat}
% =============================================================================

\subsection{Assets and Principals}

Primary assets are the sensitive columns in $\mathcal{S}$: PII fields, financial
balances, proprietary pricing terms.
Principals are enterprise departments each operating one or more AI agents.
Agents are modelled as \emph{honest-but-potentially-over-privileged}: they request
metrics they have a legitimate business need for, but not all derivation paths for
those metrics fall within their column permissions.

\subsection{Threats Addressed}

\begin{description}[leftmargin=1.2em,itemsep=3pt]
\item[T1 --- Column leakage via cached result.]
  An agent retrieves a result derived from a column it cannot see.
  \textit{Mitigation:} Algorithm~\ref{alg:retrieve} blocks the retrieval; the
  fallback recompute stays within $\mathrm{P}(d)$.

\item[T2 --- Silent metric definition drift.]
  Two teams store conflicting definitions of the same KPI under the same name.
  \textit{Mitigation:} Algorithm~\ref{alg:write} surfaces the divergence on write
  via the definition-hash conflict detector.

\item[T3 --- Stale sensitive data reuse.]
  An AMU derived from data that was sensitive at write time is retrieved after
  column permissions are updated.
  \textit{Mitigation:} the \texttt{epoch} field enables TTL-based eviction;
  sensitivity tags should be re-evaluated on retrieval when policies change.
\end{description}

\subsection{Threats Not Addressed}

\begin{description}[leftmargin=1.2em,itemsep=3pt]
\item[T4 --- Inference attacks.]
  A derived feature that \emph{encodes} sensitive information without naming the
  source column (e.g., a risk score computed from \texttt{income}) will not be
  caught unless the dependency is explicitly recorded in the lineage graph.
  This is the most important production gap.

\item[T5 --- Malicious lineage fabrication.]
  A rogue agent writes an AMU with an intentionally incomplete lineage graph,
  bypassing the gate.
  Automatic lineage extraction (Assumption~\ref{ass:complete}) is the countermeasure.

\item[T6 --- Aggregate inference.]
  A sequence of individually safe retrievals may allow reconstruction of sensitive
  values.
  Algorithm~\ref{alg:retrieve} is a per-retrieval check; it provides no differential
  privacy guarantee.

\item[T7 --- Insider threats.]
  An operator with direct store access can read or modify entries.
  The mechanism assumes a trusted store layer.
\end{description}

\section{Experiments}
\label{sec:experiments}
% =============================================================================

\subsection{Protocol}
\label{sec:protocol}

We built a synthetic discrete-event simulator in pure Python to test the mechanism
in isolation from LLM inference, network latency, and query optimiser effects.
Each run generates 120 events across 20 epochs (6 events per epoch), replayed
identically through three systems:
\textbf{No Memory} (structurally leak-free, zero reuse);
\textbf{Naive Shared Memory} (retrieval keyed on metric name only; represents the
content-gated approach of all six prior systems);
and \textbf{Lineage-Aware} (proposed; gated on $\mathrm{S}(a) \subseteq \mathrm{P}(d)$).

Three metrics are measured: \emph{leak rate} (fraction of cross-department
retrievals exposing unauthorised columns), \emph{memory reuse rate} (fraction
served from memory), and \emph{metric-conflict recall} (fraction of
ground-truth definition-divergence events flagged).
Results are reported as mean $\pm$ population standard deviation over 30 independent
random seeds; the full source code is provided in supplementary materials.

\subsection{Experiment 3: Fuzzy Conflict-Detection Study}
\label{sec:fuzzy}

\subsubsection*{Motivation}

The exact definition-hash detector (Algorithm~\ref{alg:write}) flags any two AMUs
with different $\mathrm{H}(\cdot)$ values as conflicting.
But \texttt{churn\_rate} with filter ``no txn in 90 days'' vs.\ ``no txn in 60 days''
uses the same join path and columns---only the lookback threshold differs.
Is this a \emph{true conflict} (different metric semantics) or a
\emph{threshold variant} (same metric, recalibrated)?
If D1 floods analysts with alerts for every threshold recalibration, the signal
becomes noise.

\subsubsection*{Ground Truth and Detectors}

We constructed 10 hand-labelled lineage pairs:
5 \emph{True Conflicts} (TC) where join tables or column sets differ, and
5 \emph{Threshold Variants} (TV) where the join path and columns are identical
and only a numeric threshold in $\varphi$ changes.
Three detectors are evaluated:

\begin{description}[leftmargin=1.2em,itemsep=2pt]
\item[D1 --- Exact hash.] Conflict iff $\mathrm{H}(a) \neq \mathrm{H}(b)$.
\item[D2 --- Jaccard filter ($\tau{=}0.70$).]
  When tables and columns match, conflict iff token-Jaccard of filter strings $< 0.70$;
  otherwise always flags a conflict.
\item[D3 --- Column-graph.]
  Conflict iff the union of column sets or the set of joined tables differs;
  filter-string variation is ignored.
\end{description}

\begin{table}[h]
\centering
\caption{Fuzzy conflict-detection results on 10 labelled pairs (5 TC + 5 TV).}
\label{tab:fuzzy}
\begin{tabular}{@{}lccccc@{}}
\toprule
\textbf{Detector} & \textbf{Precision} & \textbf{Recall} & \textbf{F\textsubscript{1}}
& \textbf{FP} & \textbf{FN} \\
\midrule
D1 --- Exact hash             & 0.50 & 1.00 & 0.67 & 5 & 0 \\
D2 --- Jaccard ($\tau{=}0.70$)    & 0.62 & 1.00 & 0.77 & 3 & 0 \\
D3 --- Column-graph           & \textbf{1.00} & \textbf{1.00} & \textbf{1.00} & 0 & 0 \\
\bottomrule
\end{tabular}
\end{table}

D1 has perfect recall but precision 0.50: it flags every threshold variant as a
conflict.
D2 recovers two of the five TV pairs but fails when the threshold change involves
a distinct numeric token.
D3 achieves perfect precision and recall: checking whether the
\emph{join path and column set} change is exactly the right granularity for
detecting semantic divergence, because threshold recalibrations do not alter the
underlying data dependencies.

\paragraph{Implication for the main simulation.}
The main simulation uses D1, which means the reported $100\%$ conflict recall in
Tables~\ref{tab:results1} and~\ref{tab:results2} conflates true conflicts with
threshold variants---overstating the alert rate.
A production deployment should use D3.
This does not affect the leak-rate or reuse-rate results, which depend only on
$\mathrm{S}(a)$, not on $\mathrm{H}(a)$.

\section{Discussion}
\label{sec:discussion}
% =============================================================================

\subsection{What This Work Establishes}

Three findings are robust.
First, the AMU schema and lineage gate work as a mechanism, backed by
Theorem~\ref{thm:safety}.
Second, the governance-efficiency tradeoff is quantifiable and workload-dependent:
the $\approx$13--14 percentage-point reuse cost is concentrated on the subset of
metrics with sensitive lineage variants in circulation.
Third, column-graph matching is the right granularity for conflict detection:
exact hash matching over-alerts by treating threshold variants as semantic conflicts.

\subsection{Limitations}

Three limitations constrain generalisability.

\textbf{Inference attacks (T4).}
The simulation does not test derivation paths where sensitive information is encoded
in a derived feature without naming the source column.
This is the most important production gap.

\textbf{Ground-truth scale.}
The fuzzy experiment uses 10 hand-labelled pairs.
The D3 finding is clear on this set but should be validated on a larger corpus
from a real analytics workload.

\textbf{Synthetic workload composition.}
The 18.8\% and 25.5\% naive leak rates are properties of specific workload mixes,
not estimates of real-world base rates.

\subsection{Future Work}

\textbf{Adversarial lineage testing.}
Generate queries that smuggle sensitive join paths through derived features, column
aliasing, or multi-hop derivations.
This directly stress-tests Assumption~\ref{ass:complete}.

\textbf{Automatic lineage extraction.}
Coupling the AMU mechanism with LINEAGEX~\citep{zhang2025lineagex} or a query-log
extractor would populate lineage fields automatically, removing the reliance on
agent-reported lineage and closing T5.

\textbf{Real workload evaluation.}
Replacing the simulated schemas with a real data warehouse (20--50 tables, queries
from TPC-DS or a production workload trace) would establish whether the $O(1)$
expected retrieval cost and negligible storage overhead hold at enterprise scale.

\section{Conclusion}
\label{sec:conclusion}
% =============================================================================

Every current AI agent memory system governs \emph{what} is stored and \emph{who}
may access it, but not \emph{how} the stored result was derived.
In enterprise multi-department analytics, this gap enables column-level PII leakage
through derived results and silent metric-definition conflicts---failure modes that
content-based governance cannot prevent.

The Analytical Memory Unit schema and lineage-gated retrieval policy close this gap
with minimal overhead: $4$--$8\times$ the storage of a bare value entry and $O(1)$
expected retrieval cost.
Theorem~\ref{thm:safety} provides a formal guarantee.
Simulation on both a synthetic and a TPC-H-inspired schema shows that content-gated
shared memory leaks on $18.8\%$ and $25.5\%$ of cross-department retrievals
respectively; lineage-aware gating eliminates leakage in both configurations at a
cost of $\approx$13--14 percentage points of reuse rate.
A secondary experiment establishes that column-graph conflict detection is the
right granularity: exact hash matching creates spurious conflicts for threshold
variants with precision 0.50, while column-graph matching achieves $F_1 = 1.00$.

The 0\% leakage result is a policy guarantee that follows from the theorem, not an
empirical surprise.
The substantive empirical finding is the naive baseline's structurally non-zero
leak rate, which holds consistently across 60 total seed runs and two schema
configurations.

\section*{Implementation Notes}

The reference implementation consists of:
\texttt{model.py} (AMU schema and dataclasses),
\texttt{systems.py} (three competing memory systems),
\texttt{simulate.py} (workload generator, event replay, seed sweep),
\texttt{tpch\_experiment.py} (TPC-H-inspired schema replication), and
\texttt{fuzzy\_experiment.py} (conflict-detection study).

Key reproducibility invariants:
\begin{itemize}[itemsep=1pt]
  \item \texttt{sensitivity\_tags} is computed once at AMU creation and cached.
  \item The gate check ($\mathrm{S}(a) \not\subseteq \mathrm{P}(d)$) is a Python
        \texttt{set} difference, executed in sub-microsecond time.
  \item The seed sweep calls \texttt{random.seed(s)} before each run for exact
        reproducibility.
  \item All tables are reproducible by running \texttt{python simulate.py} and
        \texttt{python tpch\_experiment.py} with the published code.
\end{itemize}
